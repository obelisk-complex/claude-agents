### Finding 1 (CRITICAL) - Fallback paragraph contradicts the file's own auditor/fixer boundary
**Situation:** New "Fallback: orchestrator-writes-directly" paragraph, inserted as an indented continuation under step 3 of `## Core workflow` (lines ~57).
**Behaviour observed:** The paragraph instructs: "If subagents fail to produce findings... the orchestrator should read the plan, run the audit reasoning directly, and write findings. This is faster and more reliable than re-dispatching." This directly contradicts three other statements already in the same file: (a) `## Scope`, "You run the loop and apply the fixes; plan-auditor and requirements-auditor find the defects"; (b) Guiding Principle 2, "The auditors find; you fix. Do not re-derive their findings or audit the plan yourself"; (c) Guiding Principle 13, "Prefer the specialist over doing it yourself... that is the tool designed for this." It also conflicts with step 4's existing remedy for a non-responding auditor ("If either is missing its `## Completion` block, re-dispatch that auditor; do not proceed on a partial round"); the new paragraph explicitly offers self-audit as "faster and more reliable than re-dispatching," i.e. an alternative to the exact behaviour step 4 mandates.
**Impact:** An agent given two contradictory instructions for the same failure mode (re-dispatch per step 4/Scope/P2/P13 vs. self-audit per the new fallback) will resolve the conflict unpredictably at runtime. Worse, if it takes the fallback path, findings the termination rule requires to come from "both auditors reported" can now originate from the orchestrator itself, silently invalidating the Verification section's explicit warning that "a zero tally from an auditor that never reported is not a zero tally." This is the exact control-integrity failure the file elsewhere works hard to prevent (`## Controls must be able to fail` cross-reference in step 3).
**Recommendation:** Either remove the fallback paragraph, or reconcile it explicitly: state that self-audit output is advisory only and cannot satisfy the "both auditors reported" termination condition, and update step 4 to reference the new fallback rather than leaving two unreconciled remedies for the same failure.

### Finding 2 (CRITICAL) - Step 9 reopens the round cap the file declares closed
**Situation:** New step 9, "Cross-model final review (mandatory on final round)" (line 69), specifically its closing clause "If the final review finds new CRITICAL/HIGH/MEDIUM findings, add a round 4 and re-audit."
**Behaviour observed:** `## Loop termination` states the round cap as `round 3 ends without meeting the rule → stalemate, escalate` and explicitly says "This is the only statement of the rule. Everything below refers to it rather than restating it." Guiding Principle 4 restates the same cap: "Three rounds, then escalate. A plan still failing the termination rule after three rounds usually needs redesign... Say which, and stop." Step 9 restates and overrides this rule from a different location in the file, introducing a round 4 without updating the canonical `## Loop termination` block or Guiding Principle 4 to match.
**Impact:** The file now contains two authorities on the round cap that disagree: the canonical rule (hard stop at 3, escalate) and step 9 (extend to 4 under a stated condition). An agent following the canonical block's own instruction to treat it as authoritative ("refer to it rather than restating it") has no way to know step 9 is meant as an exception rather than an error, since nothing marks it as one. This is the same class of internal-contradiction failure as Finding 1, in the second of the two additions.
**Recommendation:** Amend the `## Loop termination` block itself to state the round-4 exception (e.g. "round 3 ends clean but cross-model review finds new C/H/M → round 4, then hard stop") so there remains exactly one canonical statement of the rule, and update Guiding Principle 4 to match rather than leaving it saying "three rounds, then escalate" unconditionally.

### Finding 3 (HIGH) - Step 9 uses an em-dash, violating Style rules
**Situation:** Step 9, line 69: "A multi-model panel can still miss architectural blind spots — the panel shares assumptions about the architecture that a different model family doesn't have."
**Behaviour observed:** `AGENT_CHECKLIST.md` Style rules: "Use single hyphens for dashes in prose, never em-dashes or double hyphens." This sentence uses an em-dash ("—"), quoted here verbatim as evidence. No other sentence in the file uses one (confirmed: this is the only em-dash in the document).
**Impact:** Minor on its own, but it is a direct, unambiguous checklist violation in freshly-added text, and this file is the canonical example other agents in the fleet are audited against for style consistency.
**Recommendation:** Replace with a period (new sentence) or comma: "A multi-model panel can still miss architectural blind spots: the panel shares assumptions about the architecture that a different model family doesn't have."

### Finding 4 (HIGH) - Step 9's cross-model dispatch has no verifiable target and no matching frontmatter capability
**Situation:** Step 9: "run one final review through a different model family than any used in the loop... Use OpenRouter for models not available locally." Frontmatter (lines 1-15): `tools: Read, Grep, Glob, Bash, Write, Edit, Agent`, no `mcpServers:` field.
**Behaviour observed:** `AGENT_CHECKLIST.md`'s `## Dispatching other agents` requires that any agent whose `tools` include `Agent` confirm each target is "a registered, dispatchable agent type in the running harness before relying on it, not merely that a file is present in the repo." Step 3, for the two existing auditors, does exactly this ("confirm plan-auditor and requirements-auditor are registered, dispatchable agent types in this harness... if either is unavailable, substitute the nearest available auditor and record the substitution"). Step 9 names no target agent, performs no such confirmation, and gives no substitution rule if OpenRouter access is unavailable. Separately, the checklist's `mcpServers` bullet says the field is required "only if the agent references external APIs"; step 9 is now the file's only reference to an external API (OpenRouter) and no `mcpServers:` field exists. A fleet-wide grep confirms no other agent in this repository references OpenRouter and no config or doc names a mechanism for it, so there is no established fleet convention step 9 could be relying on implicitly.
**Impact:** This is the same "control that cannot fail" class the file explicitly names and works to avoid elsewhere (step 3's cross-reference to `## Controls must be able to fail`). An instruction to dispatch to "a different model family via OpenRouter" with no named target, no confirmed registration, and no declared capability to reach it cannot be told apart from an instruction that silently does nothing: exactly the failure mode step 3 was written to prevent for the other two auditors.
**Recommendation:** Either name a specific, registered agent/model configuration for the cross-model review and add the confirm-before-dispatch language step 3 already uses, or add an `mcpServers` entry plus a concrete tool-call path, or (if no such mechanism exists yet) remove step 9 until one does.

### Finding 5 (MEDIUM) - Output format template has no field for step 9's outcome
**Situation:** `## Output format` template, lines 118-153; step 9 (line 69).
**Behaviour observed:** The checklist's `## Output format` bullet requires "Template fields match everything the workflow promises to produce." Step 9 is now a mandatory, promised part of every clean run ("mandatory on final round") that can itself add a round 4. The output template's fields (`Result`, `Rounds`, `Final tally`, refactor-log table, `Auditor completion`) have no place to record whether the cross-model review ran, which model it used, what it found, or whether it triggered a round 4.
**Impact:** A caller reading the template output has no way to tell "cross-model review ran and found nothing" from "cross-model review did not run": the same distinguishability gap the report protocol and `## Controls must be able to fail` exist to close elsewhere in this file, now reopened for the newest step.
**Recommendation:** Add a field, e.g. `**Cross-model review:** [model], [clean | N new findings, round 4 triggered]`, to the output template, and to the `### Auditor completion` list (or a new subsection) so the review's completion is recorded the same way the two auditors' completion is.

### Finding 6 (LOW) - Placement mixes a one-time closing step into the per-round numbered workflow
**Situation:** `## Core workflow`, steps 1-9. Steps 1-8 execute once per round (the loop body); step 9 fires once, only after the loop's final round, conditioned on `CRITICAL=HIGH=MEDIUM=0`.
**Behaviour observed:** Step 9 is numbered as a sequential continuation of steps 1-8 with no marker distinguishing "runs every round" from "runs once, after the loop exits." The step's own title ("mandatory on final round") supplies the distinction, but only in the title text, not in the structure.
**Impact:** Minor readability/structure ambiguity: a reader skimming the numbered list could infer step 9 runs every round like steps 1-8, when in fact it runs at most once per plan.
**Recommendation:** Consider a separate un-numbered subsection (e.g. `## Final review` after `## Core workflow`) for step 9, consistent with how `## Severity handling` is already broken out rather than folded into the numbered steps. Not blocking; low confidence this rises above house style.

### Finding 7 (MEDIUM, uncertain) - `tools:` lists Grep, Glob, Bash with no corresponding reference in the body

Marked uncertain rather than asserted: this round is scoped to structural checklist conformance, not the tool-appropriateness judgment calls reserved for a token-waste round, and it is possible these three are a deliberate fleet-wide baseline for orchestrator-class agents that the checklist's "only tools actually used" bullet does not intend to catch; worth confirming against sibling orchestrators before removing.

### Finding 8 (UNCERTAIN) - `memory: project` may not fit this agent's described memory content
**Situation:** Frontmatter, line 13: `memory: project`. `## Memory` section, lines 24-25.
**Behaviour observed:** The checklist criterion: "`project` when findings are specific to the codebase the agent runs in, `user` for meta agents whose patterns generalise across projects." The Memory section's actual content, "defect classes that recur across the plans you have audited (phases with no exit criteria, rollbacks named but never specified, estimates with no slack)... which finding classes each auditor tends to produce," reads as generalising across plans and projects rather than being specific to one codebase, which by the checklist's own wording points toward `user`.
**Impact:** If `project` is wrong, memory recorded under one project's `.claude` scope would not be recalled when the same agent audits a plan in a different repository, losing exactly the cross-plan pattern recognition the Memory section asks it to build.
**Recommendation:** Marked uncertain, not asserted wrong: sibling agent `plan-auditor.md` (same domain family) also uses `memory: project` with similarly cross-plan-sounding content, so this may be a deliberate, already-established convention for the "plan" agent family (e.g. because plans themselves live inside a specific project's repo and recurring planning-culture defects are treated as project-local). Recommend confirming the intended semantics with whoever set the convention rather than changing unilaterally.

### Finding 9 (MEDIUM) - Step 9 hardcodes a dated "Confirmed" instance into evergreen methodology text, against the file's own Memory loop
**Situation:** Step 9, line 69: "Confirmed 2026-07-21: a 3-model panel (nemotron + deepseek-v4-pro + glm-5.2) found 48 gaps but missed 9 architectural blind spots that Claude Opus 4.8 caught in a single pass."
**Behaviour observed:** The file's own `## Memory` section instructs: "Update your memory after each session with the defect classes this plan showed, how many rounds it took to converge, any fix that failed re-audit and what replaced it..." A dated, "Confirmed"-labelled, specific-instance citation belongs in memory by the file's own stated architecture, not hardcoded into the Core Workflow text that is re-read on every invocation regardless of whether the cited instance is still representative. This is not an isolated observation: the same defect shape (dated "Confirmed" instance, unverifiable named model versions, baked into permanent methodology text rather than memory) was independently found the same day in `agents/blind-spot-auditor.md`'s recently-added section, per this agent's own memory (`feedback_single_agent_structural_round_patterns`), making this a recognised authoring-habit pattern rather than a one-off. Separately and unresolved: I could not verify the specific empirical claim (model names, gap counts) against any file in this repository or source in scope for this round.
**Impact:** Baking a dated instance into the always-loaded workflow text means every future invocation carries a citation that may no longer be representative, and does so in the one section (Core Workflow) that gets re-read regardless of relevance, while the Memory section built for exactly this purpose goes unused for it. Separately, if the specific empirical claim is invented rather than sourced, an agent treating "Confirmed" text in its own prompt as ground truth risks repeating it to a user as fact.
**Recommendation:** Strip the dated citation and specific numbers from step 9's body text; keep the actionable instruction ("run a cross-model review because a same-family panel can share blind spots a genuinely different model family does not") and, if the underlying result is real and worth keeping, move it to memory rather than the prompt body.
